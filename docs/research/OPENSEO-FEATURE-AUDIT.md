# OpenSEO feature audit and Treg Lens roadmap

Reviewed 20 October 2026. This audit records the baseline revisions below. The first three priorities were subsequently implemented in Lens; see the [release verification](../TEST-REPORT.md#discovery-comparable-trends-and-citation-exploration--20-october-2026) and [current product behavior](../PRODUCT-STATUS.md).

**Recommendation:** strengthen discovery continuity, measurement quality and evidence-to-action workflows first. Add optional first-party search data after those foundations. OpenSEO provides useful domain algorithms and workflow patterns; importing its whole application would expand Lens into a different product.

## Scope and confidence

Three parallel source audits covered AI measurement, broader SEO, and onboarding/agent/report workflows. This assessment compares the **current standalone Treg Lens**, not the earlier Python/Vue integration slice.

- OpenSEO: `every-app/open-seo`, commit `c5f8db19c7ca9e750836b6ed5c8a6491d4f967f4`. Fetched upstream; the existing reference fork matches upstream main.
- Lens: `tomcharlesosman/treg-lens`, commit `e3adaefc7d96fffda25365d3f98d83cd5c72c3e5`.
- Evidence: application/service/tool source, public documentation and plugin skills. Links below pin source to these revisions.
- This was a source audit. No paid research, provider benchmarking, account changes or new browser tests were performed. Existing Lens release verification is recorded separately in [the test report](../TEST-REPORT.md).
- Recommendations below describe proposed work at the audited baseline, rather than the current release status. The original audit changed documentation only.

OpenSEO targets broad SEO research for people and agents. Lens targets a narrower job: understand how selected AI answers represent a brand, inspect the evidence, decide what to improve, and measure again. This difference should determine priorities.

## What Lens already has

The latest onboarding already includes reviewed URL-led brand setup, buyer context, competitor names **and editable domains**, question intent/provenance, original research receipts, free manual setup, interrupted-research recovery, separate paid approvals, and Settings → Rerun onboarding without erasing saved work. These are implemented capabilities, not remaining roadmap items. [Profile and question contracts](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/lib/workspace-data.ts#L4), [review and save](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/components/brand-onboarding.tsx#L272).

Lens also already has four answer collectors, saved partial evidence, latest-audit findings, keyword/PAA discovery, Moz/Exa source research, daily/weekly monitoring, per-run/monthly budgets, durable isolation, CAS saves, full backups and filtered JSON/CSV reports. Its dependency footprint remains eight runtime packages. [Current product boundaries](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/docs/PRODUCT-STATUS.md#L9), [runtime dependencies](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/package.json#L30).

Keep those strengths while extending the product. OpenSEO's presence of a similar feature is not a reason to replace a working Lens implementation.

## Concrete gaps verified in current Lens

1. **Discovery starts with unrelated seeds.** Every business sees “AI agent tools” and “AI search visibility.” Use reviewed category/buyer context or request explicit relevant seeds; keep them editable and never trigger research on entry. [Hard-coded defaults](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/components/discovery-dialog.tsx#L53).
2. **Discovery provenance disappears on import.** The result includes seed, provider, keyword/PAA kind and nullable volume. Import passes only question text; the workspace appends strings. Onboarding receipts are retained, but paid discovery lacks equivalent durable continuity. [Candidate data](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/lib/discovery.ts#L21), [text-only import](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/components/discovery-dialog.tsx#L422), [workspace append](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/components/workspace.tsx#L2176).
3. **Headline changes can compare different scopes.** Daily charts pool all successful answers; the score delta compares first/last audit, without matching questions/engines. A newly added easy/branded question or a different engine mix can look like improvement. Errors and no-answer exclusions already work; the gap is comparability and visible coverage across views. [Daily aggregation](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/components/workspace.tsx#L282), [first/last delta](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/components/workspace.tsx#L654).
4. **Competitor domains stop short of measurement.** Domains are saved in the reviewed profile, while audit input and configured mention matching use names; competitors lack independent citation rates. [Reviewed domain](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/lib/workspace-data.ts#L13), [audit input](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/lib/aeo.ts#L25), [matching](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/lib/aeo.ts#L463).
5. **The source overview collapses multiple pages.** Domain aggregation keeps one representative URL, which the overview's Research action uses. Individual answer citations remain available, but a page explorer would make them discoverable across runs. [Aggregation](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/lib/workspace-data.ts#L175), [source action](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/components/workspace.tsx#L1807).
6. **Actions stop before a durable page/change plan.** Lens already provides evidence-linked findings, templates and done/reopen actions. It does not yet retain a question → target page → proposed change → follow-up measurement plan or a narrative report/agent handoff. [Existing findings](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/lib/audit-findings.ts#L14), [current briefs](https://github.com/tomcharlesosman/treg-lens/blob/e3adaefc7d96fffda25365d3f98d83cd5c72c3e5/src/components/workspace.tsx#L2343).

## Recommended delivery order

These are implementation slices, not promises about development duration.

### 1. Relevant discovery with retained evidence — P0

Make the next research action fit the user's business, and preserve what they bought.

- Default to reviewed topic/category context, or useful empty-state guidance when context is insufficient. Do not make another model call just to populate defaults.
- Retain a bounded discovery receipt: original inputs, locale, candidates, providers, partial errors, completion time, quote and known/unknown billing; retain call IDs where supplied.
- Store candidate provenance alongside imported prompt identity. Generated suggestions, observed PAA, keywords, future dataset questions and first-party queries remain distinguishable.
- Acknowledge durable save before reporting successful import. Closing/reloading or choosing no candidates must not silently discard returned paid research; retain recovery/export on save failure.
- Preserve existing tracked questions, deduplicate deliberately, and never repeat interrupted paid research automatically.

**Acceptance:** unrelated business fixtures get relevant/editable defaults; paid results survive close/reload/backup/restore; stale saves preserve both versions; unknown volume/cost stays unknown; no paid request runs before approval.

### 2. Stable questions and comparable measurement — P0 foundation

Add stable prompt records with original wording, intent/topic, provenance and archive/pause state. Editing wording starts a new identity; historical answers retain their original identity and run configuration. Migrate older string-based data compatibly without inventing missing historical metadata.

Define a comparison cohort from prompt identity, engine, collector/model, market and brand identity. Show separate mention and owned-citation rates with answered/requested coverage. A missing or failed collection is not confirmed absence. Hide headline deltas for incompatible or insufficient scopes; any optional overlap-only comparison must explicitly disclose exclusions. Neutral and branded questions need separate cohorts.

Keep inventory size separate from the eight-question execution cap. Archiving a question must not silently modify an already consented monitoring schedule; show that relationship and require a deliberate schedule edit.

**Acceptance:** adding questions, switching engines, repeated checks, empty answers, changed brands and low coverage cannot fabricate progress; daily weighting is documented; legacy imports remain inspectable; original answers/receipts are unchanged.

### 3. Page-level citations and competitor evidence — P1

Add pages/domains navigation, owned/competitor/other filters, per-engine counts and exact answer drilldowns. Use reviewed competitor domains for independent citation ownership, with safe hostname/subdomain matching. Snapshot identities for new runs; do not silently rewrite old results after profile edits.

Research should target the page the user selected. Opening saved evidence, changing grouping and comparing saved answers make no provider calls.

**Acceptance:** two pages on one domain remain separately visible/researchable; repeated links count once per answer for coverage; missing competitor domains are explicit; every displayed gap opens its saved evidence.

### 4. Context → action → report → agent — P1

Extend optional context with current goal/timeframe, differentiators, important owned pages and writing preferences. Keep first-run setup skippable and short; expose deeper context after initial value.

Add a saved page plan: buyer question, existing/proposed/later page, evidence links, editable rationale, status, change date and follow-up measurement scope. A deterministic brief can use existing evidence; optional fresh research/model drafting needs its own approved quote.

Provide a private printable report with visible scope, coverage, caveats, sources and exact answer references. Preserve a reproducible evidence snapshot/version. Browser print avoids a new PDF runtime.

Add “Continue with your agent”: a credential-free context/evidence pack, copyable task and a few focused skills for interpreting saved results, planning page improvements and reporting. The pack must state that more paid work needs approval. Do not claim connection merely because a prompt was copied. A later read-only adapter can provide context, runs, answer/source detail and bounded reports without exposing full workspace replacement as the default write operation.

**Acceptance:** edits survive rerun/reload/import and stale revisions; another brand's context does not leak; report metrics match the selected cohort; print works; partial data is honest; handoff has no session/key/monitor credentials and never repeats research by itself.

### 5. First-party data and bounded diagnostics — P2
